# JeekMusic 需求文档

> 状态：草案 v0.2 · 2026-10-16

## 1. 产品定位

JeekMusic 是一个 **Android 端本地音乐播放器**，开源，以作者自用为主。

- **简洁好用**：界面干净，核心功能做精，Material You 风格。主要的使用场景是在**歌曲列表**里浏览和点播；播放页就是歌词页。
- **纯本地**：音乐只来自设备上的文件，不接入任何流媒体服务。唯一的联网功能是可选的在线歌词，默认关闭。
- **以文件夹为中心**：用户指定若干音乐文件夹，曲库围绕这些文件夹组织，同时提供按艺术家浏览的视图。常听的艺术家可以固定到标签栏，点一下直达。
- **轻、快、不损音质**：启动快，平时几乎不耗资源，同时不对音频做任何有损处理（见 §4.1）。

### 非目标（明确不做）

- 在线音乐平台、自建服务器（Navidrome / Jellyfin / WebDAV / SMB）等远程来源
- 修改音频文件的标签（应用内的"运动 / 安静"标签只保存在 App 数据里，不写进文件）
- iOS / 桌面端
- 音效类功能：均衡器、可视化频谱、动态模糊背景等（会增加耗电或改变音质）

## 2. 目标用户与使用场景

- 手机里存了大量本地音乐（mp3 / flac / m4a 等）、自己按文件夹整理曲库的用户。
- 曲库标签质量参差不齐，常见情况包括中文标签乱码、一首歌有多个艺术家、合辑、文件完全没有标签等。
- 典型场景：通勤时戴耳机听歌、跑步健身时听"运动"、睡前听"安静"并定时停止、在车上用蓝牙播放。

### 3.6 智能标签：运动 / 安静

| ID | 需求 | 优先级 |
|---|---|---|
| M-1 | 提供两个智能标签：**运动**（节奏快、能量高，适合跑步健身）和**安静**（舒缓、轻柔，适合睡前和专注） | P1 |

| M-8 | 设置里可以调整识别的灵敏度（宽松 / 标准 / 严格）。调整后立即生效，不需要重新分析音频 | P2 |

### 3.15 CUE 整轨

整轨是指一整张专辑存成一个音频文件，再配一个 `.cue` 文件描述每首歌的起止时间。中文无损资源里很常见。

| ID | 需求 | 优先级 |
|---|---|---|
| CUE-1 | 识别 FLAC / WAV 整轨文件旁边的同名 `.cue` 文件，以及 FLAC 内嵌的 cuesheet，把整轨拆成多首虚拟歌曲 | P1 |
| CUE-2 | 虚拟歌曲和普通歌曲在所有地方的表现都一样，包括文件夹视图、艺术家视图、专辑页、搜索、播放列表、智能标签和续播；整轨文件本身不在曲库里单独出现 | P1 |
| CUE-3 | 歌曲信息取自 CUE：歌名（TITLE）、艺术家（PERFORMER）、音轨号；CUE 顶层的 TITLE 作为专辑名，PERFORMER 作为专辑艺术家；CUE 里缺少的字段取自整轨文件本身的标签 | P1 |
| CUE-4 | 自动识别 CUE 文件编码（GBK 编码的 CUE 很常见），与 LY-7 使用同一套规则 | P1 |
| CUE-5 | CUE 中写的文件名和实际文件对不上时（常见于 WAV 转成 FLAC 之后，CUE 里写的仍是 `.wav`），按"同名不同扩展名"匹配；如果目录里只有一个整轨文件和一个 CUE 文件，直接配对 | P1 |
| CUE-6 | 同一个整轨中相邻两首连续播放时，尽量做到无缝衔接（现场专辑、古典乐不应该在曲间出现停顿） | P1 |
| CUE-7 | 歌词：先找 `<音轨号>. <歌名>.lrc`，再找 `<歌名>.lrc`；在线歌词按 `<音轨号>. <歌名>.lrc` 保存 | P2 |
| CUE-8 | 一个 CUE 引用多个文件、每个文件只是一首歌的情况（"分轨 CUE"），按普通单曲处理，忽略 CUE | P1 |

### 3.16 数据备份

播放列表、运动 / 安静的手动修正、固定的标签和设置只保存在 App 里，换手机或重装后就会丢失。所以要把它们自动备份到音乐目录里，跟着音乐文件一起走。

| ID | 需求 | 优先级 |
|---|---|---|
| B-1 | **自动备份**：上述数据有变化时（延迟合并），自动导出为 JSON 文件，写入**每一个**音乐文件夹下的 `.jeekmusic/backup.json`。无论将来拷走的是哪个文件夹，都能恢复 | P1 |
| B-2 | 备份内容：播放列表、手动标签修正、固定标签、歌词时间偏移、设置。歌曲用"相对于音乐文件夹的路径"引用，所以音乐文件夹换了位置（比如从内部存储挪到 SD 卡）也能对上 | P1 |
| B-3 | **自动恢复提示**：添加音乐文件夹时，如果发现里面有备份文件，并且是首次添加文件夹（或者当前 App 里没有对应的数据），提示"发现备份（时间、包含 N 个播放列表等），是否恢复？"。恢复在扫描完成后进行，对不上的歌曲在恢复结束时报告数量 | P1 |
| B-4 | 设置里提供"立即备份"和"从备份恢复"（可以选择任意备份文件） | P1 |
| B-5 | 备份中还可以包含智能标签的分析结果，换手机后不用重新分析几个小时 | P2 |
| B-6 | 写入方式是先写临时文件再替换，同时保留上一份备份（`backup.prev.json`），避免写到一半时断电导致备份损坏 | P1 |

## 4. 非功能需求

### 4.1 设计原则：简洁、省电、不损音质、快

**音质：不做任何有损处理**

- 播放时 App 不做重采样、均衡、音量标准化或其他 DSP；除睡眠定时渐弱外，App 不改变音量
- 无损格式（FLAC / ALAC / WAV）完整解码；高位深（24-bit）音源以浮点 PCM 输出，不截断到 16-bit
- 系统混音器之后的处理（如部分手机会统一重采样到 48kHz）不在 App 的控制范围内；USB DAC 比特完美输出（Android 14+）列为 P2

**省电：没在用的时候什么都不做**

- 只在播放时持有唤醒锁；不播放时没有任何后台活动（后台扫描和分析除外，且受 L-5 / M-5 约束）
- 熄屏或 App 在后台时使用硬件解码直通（音频 offload），交给音频 DSP 解码，CPU 可以休眠。设备不支持时自动回退到普通播放。设置项"低功耗播放"有三档：仅后台 / 熄屏（默认）、始终使用（包括前台，进度和歌词同步可能变粗，拖动进度条和切歌的响应变慢）、关闭
- 界面不做无谓的刷新：进度条只在可见时更新；没有可视化频谱、动态背景、按封面取色等消耗
- 智能标签分析默认只在充电时进行
- 默认不联网

**启动快**

| 指标 | 目标（中端机型，曲库 1 万首） |
|---|---|
| 冷启动到首帧（TTID） | < 400ms |
| 冷启动到列表内容完整显示（TTFD） | < 700ms |
| 温启动 | < 200ms |

做法（详见设计文档 §9）：首屏数据直接读本地缓存；扫描、分析、播放服务连接等全部推迟到首帧之后在后台线程进行；启动时恢复上次的标签、滚动位置和迷你播放条内容；使用 Baseline Profile 预编译关键路径。

测试素材：

| 来源 | 工具 | 内容 |
|---|---|---|
| 合成音频 | `tools/push-testdata.sh` | 60 首带中文、多艺术家标签的 MP3，1 首无标签（文件名推断），3 首 24-bit/96kHz FLAC |
| 真实曲库子集 | `tools/pick_library_sample.py` | 从 `D:\Mobile\Song\散曲`（1604 个文件，16GB）中挑出边界情况：带 .lrc 的歌曲、ogg/flac/wma、无标签、多艺术家、内嵌歌词、疑似 GBK 乱码，约 1.2GB |

`D:\Mobile\Song\散曲` 的统计结果（2026-10-16）：MP3 1578 首（ID3v2.3 占 80%，v2.4 占 20%，无 ID3v2 的 5 首），ogg 16、flac 2、wma 1、lrc 5；无标题和艺术家标签 21 首；内嵌歌词 5 首；疑似 GBK 乱码 1 首；**艺术家标签中出现 `/` 187 次、`&` 13 次、`,` 5 次、`feat.` 2 次**。文件名几乎都是"艺术家 - 标题"格式。

注意事项：

- **OriginOS 的 USB 安装需要在手机上确认**（"继续安装"），超时就会失败。所以需要反复安装的工作优先放在模拟器上做
- 开发期间真机开启了"插 USB 时保持唤醒"（`adb shell svc power stayon usb`），恢复默认用 `adb shell svc power stayon false`

- **启动目标是按中端机定的**，旗舰机的测量结果会偏乐观。在 X200 Ultra 上测量时，内部按更严格的标准要求（TTID < 250ms，TTFD < 450ms）；最好再找一台中端机或低配模拟器复核
- **OriginOS 的后台管理比较激进**：要验证三件事，一是前台服务播放时长时间熄屏不被杀，二是充电时 WorkManager 的分析任务能被调度，三是从系统媒体控件"恢复播放"能正常工作。必要时在设置里加一个指引，引导用户把 App 加入"允许后台高耗电"
- 骁龙平台支持音频 offload，正好用来验证"低功耗播放"的三档设置以及耗电对比
